# bcard — the scannable business card

**https://www.prasanjeet.com/bcard/** shows the QR. Scan it → the card fills
the screen and saves itself with a datetime filename → tap the card → the
splash video plays fullscreen with sound.

Browser APIs only, no build step and no server. Copied from
`ai automation/barcode-card/client`; `card.css`, `card.js`, `vendor/` and
`assets/` are byte-identical to that build. What differs is the entry point —
upstream serves the card at the folder root and keeps the QR on `qr.html`, and
those two are swapped here.

```
bcard/
├── index.html      the launcher — the QR, and what /bcard/ opens
├── card.html       the card page — what the QR points at
├── card.css        styles, animations, ambient glow, orbiting border
├── card.js         save / share / fullscreen / splash logic
├── vendor/
│   └── qrcode.min.js   QR encoder, bundled locally (24 kb, no CDN)
├── make-qr.mjs     optional: writes qr.png from the command line
├── qr.png          encodes https://www.prasanjeet.com/bcard/card.html
└── assets/
    ├── prasanjeet-product-style-3.png   the card
    └── splash.mp4                       the logo animation
```

## The two pages

| Page | What it is |
|---|---|
| `index.html` | The launcher. `/bcard/` lands here — it draws the QR on screen to scan off a monitor, and offers it as a PNG for printing. |
| `card.html` | The card. This is what the QR opens. |

`index.html` builds the QR **in the browser** from `location`, so it always
encodes wherever the folder actually is — localhost, LAN IP, or the live domain
— with nothing to regenerate.

It targets `card.html` explicitly rather than the folder. Pointing it at the
folder would resolve back to `index.html`, and scanning would just show the QR
again — keep the filename in that `new URL(...)` call if you edit it.

Every path in `card.html` and `card.js` is relative, which is what lets the
folder sit at `/bcard/` rather than a domain root. The host redirects `/bcard`
to `/bcard/` on its own, so both spellings work, and the apex domain 301s to
`www`.

### Where this is actually hosted

Two hosts serve this same repo, which is worth knowing before you debug anything:

| URL | Served by |
|---|---|
| `https://www.prasanjeet.com/bcard/` | **Netlify** — deploys automatically on push to `main` |
| `https://prasanjeetd.github.io/bcard/` | GitHub Pages, straight from the branch |

The custom domain is the Netlify one — there is no `CNAME` file in this repo
because Netlify handles the domain itself. That distinction matters: Netlify can
run server-side functions, GitHub Pages cannot.

The main site deliberately does not link here — this is reached by scanning the
QR, or by typing the URL.

## Preview locally

```bash
npx serve . -l 5173
```

`http://localhost:5173/bcard/` on the laptop is the QR; scan it with a phone on
the same Wi-Fi and you land on the card. Serve the repo root rather than this
folder so the local path matches production.

`?debug=1` on the card prints an on-screen trace — the static build has no
endpoint to post logs to, so the overlay is the whole story.

## Reprinting the QR

Open https://www.prasanjeet.com/bcard/ and hit **Download QR for printing**; it
encodes the live URL automatically. `make-qr.mjs` does the same from a
terminal, but needs the `qrcode` package, which this repo does not carry — run
it from the `barcode-card` project instead:

```bash
node make-qr.mjs https://www.prasanjeet.com/bcard/card.html   # writes qr.png
```

## Swapping the card or video

Replace the files in `assets/`. If you rename them, update the two paths in
`card.html` and the `CARD` object at the top of `card.js`. `CARD.base` sets the
download filename prefix; the datetime is appended automatically.

Note the card artwork has a QR printed into the image itself. That one is baked
into the PNG and is not generated by anything here — changing `qr.png` or the
launcher has no effect on it.

### Always re-encode a new video before dropping it in

iPhone Safari refused the original export outright — `play()` rejected with
`NotSupportedError` on every tap, which is what the "video does nothing on
iPhone" reports were. It was not the codec: that file was already H.264 High
3.1 / yuv420p / AAC-LC and decoded clean. The generator had wedged a 45 kB
`uuid` "manifest" box between `ftyp` and `moov` — exactly where a demuxer looks
for `moov` — and both exports from that tool carried the identical box. Chrome
and Android skipped it; iOS did not.

So run any replacement through ffmpeg rather than using the export directly:

```bash
ffmpeg -i new-export.mp4 \
  -c:v libx264 -profile:v main -level 3.1 -pix_fmt yuv420p -crf 20 -preset slow \
  -c:a aac -b:a 128k -ar 44100 -ac 2 \
  -movflags +faststart -map_metadata -1 -map_chapters -1 \
  splash.mp4
```

`-map_metadata -1` is the part that drops the offending box; `+faststart` puts
`moov` ahead of `mdat` so playback can begin before the file finishes. Verify
with `ffprobe`, and check the atom order is `ftyp moov free mdat` — if you see
`uuid` in there, it will fail on iPhone again.

## Notes

- **HTTPS is required in practice.** `navigator.share` needs a secure context,
  which means HTTPS or `localhost` — `file://` will not do. Both hosts serve
  HTTPS, so the deployed page is fine. Fullscreen and the download attribute
  work either way.
- **Saving is best effort, by design.** Chrome permits one automatic download
  per page load and silently drops the rest — no error, no event, nothing a
  page can detect. That is why the Save button is always on screen rather than
  appearing only after a failure.
- **Share exists for phones where downloads are blocked entirely.** If Android's
  download manager is disabled or denied storage, no download will ever land.
  The share sheet hands the PNG to Photos / Files / Drive instead and bypasses
  the Downloads folder completely. The button only appears where the browser
  actually supports sharing files.
- **`.nojekyll` at the repo root** keeps GitHub Pages from running the files
  through Jekyll. It only affects the `github.io` URL — Netlify ignores it — but
  leave it in place so both hosts behave the same.
- **Cache busting** is the host's job. Both send ETags, but if you overwrite
  `card.js` in place, hard-refresh once.
